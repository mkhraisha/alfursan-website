### Fixed

- Fixed the public-visibility rule (WordPress migration Part 3) gating a vehicle's public visibility on `photography_status = 'done'` instead of whether it actually has any uploaded photos. `photography_status` is a staff-managed flag ("have we physically photographed this car") set independently of whether those photos were ever uploaded into the DMS — most commonly via the CSV/OpenLane import sheet — so it could be `'done'` with zero photos on file, making a vehicle publicly visible with nothing to show. Found via a real production data audit: 37 of 96 vehicles were in exactly this state. `isPubliclyVisible()` (`src/lib/vehicles.ts`) and both the list and single-vehicle branches of `GET /api/vehicles` now check `images_json` is non-empty instead. `photography_status` is unaffected as a field — still shown and editable on the vehicle detail page — it just no longer gates the public site. Confirmed against a local Supabase stack: a vehicle with real photos and `photography_status = 'pending'` is now visible; a vehicle with `photography_status = 'done'` and no photos is now hidden, on both endpoints.
- Fixed the public CSP's `img-src` directive blocking vehicle photos in local dev: it was hardcoded to `'self' data: https:`, so a vehicle image served from a local Supabase stack (`http://127.0.0.1:54321/storage/...`, plain HTTP) was silently blocked by the browser — surfaced by WordPress migration Part 5's pages rendering photos straight from Supabase Storage for the first time. New `buildImgSrc()` in `src/middleware.ts` mirrors the existing `buildConnectSrc()` fix for the same class of problem (PR #62): allows the exact local Supabase origin in dev only, stays `https:`-only in production.
- Fixed `InventoryFilters.tsx` (a client-hydrated component) importing `BODY_TYPES` directly from `src/lib/vehicles.ts` — that module pulls in `zod` and every other server-oriented validation dependency it uses, so the import shipped all of it to the browser just for an 8-item dropdown list, and triggered a Vite dev-server dependency-optimization race that surfaced as sporadic `504 (Outdated Optimize Dep)` console errors and downstream page-hydration failures. Added `PUBLIC_BODY_TYPES` to the client-safe `src/lib/public-vehicle-view.ts` instead (kept in sync with `vehicles.ts`'s `BODY_TYPES` via a same-values unit test) so client components never import the validation module at all.
- Fixed the WordPress photo migration (`scripts/migrate-wordpress-photos.mjs`, Part 4) failing to complete real production runs with per-image `upload failed: fetch failed` errors and never writing `images_json` for the affected vehicles. The real error-cause diagnostics added while investigating this (see below) revealed the actual root cause once reproduced with logging on: `ERR_SSL_ALERT_BAD_RECORD_MAC` and `ERR_HTTP2_INVALID_SESSION` — Node-core HTTP/2 stack error codes, not rate limiting or anything about the files themselves (their content/size was also checked directly and is unremarkable — ordinary sub-500KB JPEGs). This is a known class of bug where Node's `fetch` (undici) HTTP/2 connection reuse misbehaves under concurrent requests to the same host. Fixed by forcing plain HTTP/1.1 for every request this script makes — both the WordPress downloads and the Supabase client (`undici`'s `Agent({ allowH2: false })`, passed as `global.fetch` to `createClient` and used directly for WP fetches) — which sidesteps the HTTP/2 code path entirely. Along the way: (1) neither the WP download, the Supabase upload, nor the final `vehicles` row update was retried at all, so any transient failure permanently failed that step; (2) once retries were added, a retried upload could legitimately come back `"the resource already exists"` — the *previous* attempt's write had actually succeeded server-side even though its response errored on the client — and that was being treated as a fresh failure instead of the success it was, burning through all remaining attempts. All three steps (download, upload, DB update) now get up to 4 attempts with backoff, an "already exists" response is treated as success (the deterministic `wp-NN` naming means it can only mean this exact image already landed), and error messages surface the underlying network cause instead of just "fetch failed". A vehicle that still ends a run with some images missing is no longer stuck: re-running the same command now detects the partial `images_json` and fetches only what's still missing, preserving correct WP photo order regardless of which subset succeeded on which run. Reproduced the exact failure end-to-end against a local Supabase stack before and after the fix, and re-validated against the specific real vehicle from the user's error report.
- Fixed the WordPress inventory migration (`scripts/migrate-wordpress-inventory.mjs`) flattening the public `description` into a single run-on line and dropping the Carfax report link entirely. WP post bodies wrap each section in its own `<p>`/`<div>`/heading tag and embed the Carfax link as an in-body `<a href="https://vhr.carfax.ca/...">` — the old `stripHtmlToPlainText` stripped every tag to a space, losing all paragraph structure and discarding the link's `href` along with the tag (leaving only dead text like "Carfax Report" behind). `stripHtmlToPlainText` now turns block-tag boundaries and `<br>` into blank lines and drops now-empty spacer paragraphs; a new `extractCarfaxLink()` pulls the Carfax URL out before the description is flattened, and `mapWpCarToVehicleRow` now sets it on `carfax_link` (added to `FILLABLE_FIELDS`, so an existing vehicle missing a Carfax link gets it filled in on re-run, same as the other WP-only fields).
- Fixed the Google Maps embed on `/contact-us` never rendering — the global `Content-Security-Policy` in `src/middleware.ts` had no `frame-src` directive, so it fell back to `default-src 'self'`, and every browser correctly blocked the cross-origin `https://www.google.com/maps/embed` iframe (silently — no visible error on the page itself). Added `frame-src https://www.google.com`.
- Fixed `GET /api/admin/export-application` and `PATCH /api/admin/update-application` being unreachable by legitimate admins in production — both relied on `Astro.locals.adminRole`/`adminEmail`, but `src/middleware.ts` only populates `Astro.locals` for paths starting with `/admin/`, not `/api/admin/`, so those fields were always `undefined` and every request was denied (fail-closed — not a data leak, but the Export/Update Application admin features were completely non-functional). Found while auditing that public endpoints only expose public columns. Both routes now authenticate directly via `getRequestUser()`, the same way every other `/api/**` route does.
- Fixed the expense CSV importer rejecting rows whose `tax_amount`/`amount` column contained sub-cent floating-point residue from a spreadsheet formula (e.g. `-0.0000000000004`, displayed as `$0.00`) — `parseCurrency` now rounds parsed values to the nearest cent, so this no longer trips the `tax_amount >= 0` check for vendors that charge no tax.
- Fixed the admin **Account** page (`/admin/account/`) getting stuck on "Loading…" forever and never showing registered passkeys — an automated PR-finding autofix had silently dropped the `supabase.auth.passkey.list()` call in `loadPasskeys()`, leaving it reference undeclared variables (a runtime `ReferenceError` that `npm run build` doesn't catch, since it doesn't type-check). The page now also shows a persistent, dismissable error message with a Retry button instead of failing silently, and displays which account's passkeys are being managed. Added `npm run astro:check` as an npm script so the project's full TypeScript check (which *would* have caught this) is actually runnable.
- Fixed the remaining `astro check` type errors (61 → 0 once combined with the passkey fix above). Most were Supabase query-builder type errors — passing a role-conditional `.select("...")` string built from a ternary breaks Supabase's type-level column parser (it can only parse a single string literal, not a union of two), producing an opaque `ParserError` type wherever the result was used. Split each of these into two full query branches (one per literal `.select()` string) in `/api/vehicles`, `/api/vehicles/[vin]`, and the admin inventory list/detail pages. The rest were pre-existing type gaps in test mocks (`middleware-cache-control.test.ts`, `middleware-token-refresh.test.ts`, `check-env.test.ts`, `security.test.ts`, `api-upload-url.test.ts`) — fixed with accurate casts/types rather than loosening `tsconfig.json`.
- Stopped creating a Sentry release/deploy on every build (including PR preview deploys) — `astro.config.mjs` now only creates and finalizes a Sentry release, and records a deploy, when `VERCEL_ENV` is `production`. Preview builds still upload source maps for the runtime SDK's error reporting.
- Fixed the "Listing" link on the admin finance application view, which pointed at the non-existent `/listings/` route instead of `/listing/`.
- Fixed the homepage auto-scrolling ~2000px down on every load: the Popular Makes tab strip called `scrollIntoView` on mount instead of only on user-driven tab changes.
- Fixed the financing application form's two-column field rows (Full Legal Name / Date of Birth, Phone / Email, etc.) never collapsing to one column on mobile, which truncated placeholder text and cramped inputs on narrow screens.
- Fixed magic-link admin sign-in bouncing back to the login page: `/admin/**` responses (page renders and the middleware's own redirects) had no explicit `Cache-Control` header, so Vercel's edge could heuristically cache an anonymous login-redirect (e.g. from the daily smoke test hitting production unauthenticated) and serve it back to a freshly-authenticated user. The middleware now sets `Cache-Control: no-store` on every `/admin/**` response.
- Fixed admin sessions intermittently bouncing to `/admin/?error=invalid_token` on later-visited pages (most noticeably Garage Register and Users): the `sb-token-exp` cookie was accidentally marked `HttpOnly` on token refresh (in `middleware.ts` and `refresh-session.ts`), contradicting its intentional non-`HttpOnly` design in the initial login cookie writer. This silently broke the client-side proactive-refresh timer after the very first refresh of a session, letting the access token genuinely expire later on with no safety net beyond a single reactive refresh attempt. `sb-token-exp` is no longer marked `HttpOnly` on rotation.
- Fixed the dashed border on the CSV importer upload zones (vehicle and expense import) not wrapping the full box — the underlying `<label>` was an inline element, so the border only hugged its inline content instead of the padded area around it. The upload zone is now a flex container.
- Fixed the homepage's first Featured Listing (hero card) photo being hidden behind its text overlay on mobile. The overlay was absolutely positioned over the image, and on narrow screens the shrunken (16:9) image was often shorter than the overlay's text content, so the opaque overlay panel grew tall enough to cover the entire photo. The hero card's text now flows below the image on mobile instead of overlaying it, matching the other listing cards.
- Hardened the vehicle CSV importer (`CSVImport.tsx`) against oversized files and function-invocation failures, matching the expense importer: a client-side ~4 MB file-size guard before upload, and a specific, actionable error message when the API returns a `FUNCTION_INVOCATION_FAILED` error instead of a generic "Preview/Import failed".
- Fixed vehicle/expense CSV imports (and other mutating API endpoints) being served through Vercel's ISR edge cache instead of running fresh on every request: the adapter's `isr` config had no `exclude` list, so every non-prerendered route — including POST-only endpoints like `/api/vehicles/import` and `/api/vehicles/expenses/import` — was routed to the shared `_isr` function, which caches by path alone and ignores HTTP method. `astro.config.mjs` now excludes `/api/**` from ISR so all API routes run as plain serverless functions and respect their own `Cache-Control` header. Also added the missing `Cache-Control: no-store` header to several API route responses (`/api/vehicles/import`, `/api/vehicles/expenses/import`, `/api/admin/set-session`, `/api/admin/refresh-session`, `/api/admin/update-application`, `/api/finance`, `/api/finance/phase2`, `/api/finance/upload-url`, `/api/vehicles/upload-url`, `/api/dealer/users/[userId]`, `/api/vehicles/[vin]/commission`, `/api/vehicles/[vin]/expenses/[expenseId]`, `/api/vehicles/[vin]/documents/[docId]`) that were previously relying on caches to heuristically treat them as non-cacheable.
- Fixed the admin site continuously reloading/signing users out in a loop: the same ISR gap that affected `/api/**` above also applied to every `/admin/**` page — `astro.config.mjs`'s `isr.exclude` only listed `/api/**`, so admin pages were still routed through Vercel's shared `_isr` function and cached at the edge for up to 3 hours despite the app's own `Cache-Control: no-store` header (that header only governs downstream/browser caching, not the ISR function's own edge cache). A cached admin response could replay stale, already-rotated `sb-access-token`/`sb-refresh-token`/`sb-token-exp` cookies from a prior session refresh; the client-side proactive-refresh timer in `AdminLayout.astro` would then fail to refresh the already-consumed refresh token and force a `window.location.href` redirect to sign-out, which could itself be served from cache, repeating the cycle. `astro.config.mjs` now also excludes `/admin/**` from ISR.
- Fixed the entire production build crashing whenever the WordPress API had a transient outage: `getStaticPaths()` for `/blog/[slug]` (and any other prerendered page backed by `wordpress.ts`) let a network-error exception from `fetchWithRetry` propagate uncaught after retries were exhausted, killing the whole `astro build` instead of degrading just the affected page — unlike a persistent HTTP 4xx/5xx response, which every caller already handled gracefully. `fetchWithRetry` now returns a synthetic non-ok `Response` instead of throwing, so existing `!response.ok` handling in `getPosts`/`getPostBySlug`/`getPageBySlug`/`getCars`/`getCarBySlug` applies uniformly. Found via two flaky CI runs on an unrelated PR.
- Fixed every table-backed API route 500ing ("permission denied for table ...") when run against a fresh local Supabase stack (`supabase start` + `supabase db reset`): the CLI's local template never applies the `GRANT`s that Supabase's hosted platform sets up automatically at project creation, so `anon`/`authenticated`/`service_role` had no SELECT/INSERT/UPDATE/DELETE on any public-schema table — RLS was never even reached. Added a migration that grants baseline privileges and default privileges for future tables. Idempotent; no effect on production, which already has these grants. This also unblocks running the e2e suite against a real local backend (see CI changes below).
- Fixed every `/admin/**` and `/api/**` route 404ing in production when visited with a trailing slash (e.g. `/admin/dashboard/`, the app's own convention) — a regression from excluding those routes from ISR above. `@astrojs/vercel`'s route-regex generation for `isr.exclude`d routes builds the Vercel routing regex from the route's plain path string via a helper meant for static redirects, instead of reusing Astro's own precompiled route regex, silently dropping the optional trailing-slash group that `trailingSlash: "ignore"` normally compiles in. Every excluded route (all of `/admin/**` and `/api/**`) was affected: a trailing-slash request fell through to Vercel's catch-all 404 route instead of reaching the page. Patched via `patch-package` (`patches/@astrojs+vercel+11.0.3.patch`) to reuse the route's own compiled pattern regex. This is why the e2e suite didn't catch it: `playwright.config.ts` runs against `astro dev`, which uses Astro's own routing and never exercises the adapter's build-time route generation — added `src/__tests__/vercel-output-trailing-slash.test.ts`, which inspects the actual `.vercel/output/config.json` produced by `npm run build` (which CI already runs before `npm test`), to catch this class of regression going forward.

### Fixed

- Fixed the authenticated CRUD/RBAC e2e tests (`e2e/vehicles-api.spec.ts`) failing on every DELETE and CSV-import call once real tokens were wired up: Astro's built-in CSRF origin-check middleware 403s any non-GET request that has neither a matching `Origin` header nor a non-form `Content-Type`, which covers bodyless DELETEs and `multipart/form-data` uploads made by non-browser HTTP clients. Real browsers always send `Origin` on same-origin fetches, so production and the admin UI were never affected — only test tooling (and any headless API client) hit this. Tests now send an explicit `Origin` header matching the app's own origin. This had never surfaced before because the RBAC/CRUD suite had never actually run anywhere until this change.
- Fixed the entire production build crashing whenever the WordPress API had a transient outage: `getStaticPaths()` for `/blog/[slug]` (and any other prerendered page backed by `wordpress.ts`) let a network-error exception from `fetchWithRetry` propagate uncaught after retries were exhausted, killing the whole `astro build` instead of degrading just the affected page — unlike a persistent HTTP 4xx/5xx response, which every caller already handled gracefully. `fetchWithRetry` now returns a synthetic non-ok `Response` instead of throwing, so existing `!response.ok` handling in `getPosts`/`getPostBySlug`/`getPageBySlug`/`getCars`/`getCarBySlug` applies uniformly. Found via three flaky CI runs across this PR stack.

Slashes (and any run of whitespace/hyphens/slashes) now collapse to a single underscore.

### Fixed

- Fixed magic-link admin sign-in never completing against a local Supabase stack: `supabase/config.toml`'s `[auth] site_url`/`additional_redirect_urls` were set to `http://127.0.0.1:3000` / `https://127.0.0.1:3000`, but the dev server (and the login page's `emailRedirectTo`) actually run on `http://localhost:4321`, so GoTrue rejected the magic-link redirect target. `site_url` now points at `http://localhost:4321` and `additional_redirect_urls` includes the actual callback path on both `localhost` and `127.0.0.1`.
- Fixed the local Supabase stack issuing 1-hour admin sessions instead of the intended 8 hours: `supabase/config.toml`'s `jwt_expiry` was left at the CLI's default (`3600`) instead of `28800`, the value the admin cookie/refresh code (`src/middleware.ts`, `src/pages/api/admin/set-session.ts`, `src/pages/api/admin/refresh-session.ts`) already assumed as its fallback session length. Local `jwt_expiry` is now `28800` (8 hours), matching that intent. **Production's JWT expiry is a separate hosted setting** (Supabase Dashboard → Authentication → Sessions → "Access token (JWT) expiry limit") and isn't managed by this repo — update it there to 28800 seconds to get the same 8-hour session in production.
- Fixed the browser blocking the magic-link request against a local Supabase stack with a Content-Security-Policy `connect-src` violation: the admin CSP hardcoded `connect-src 'self' https:`, which never allowed plain-HTTP origins like `http://127.0.0.1:54321`. `src/middleware.ts` now adds the local Supabase origin to `connect-src` only in dev (`import.meta.env.DEV`); production stays locked to `https:` only.
